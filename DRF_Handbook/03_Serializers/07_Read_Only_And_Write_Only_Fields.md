# Introduction

Read-only fields appear in serialized output but are not accepted as writable client input. Write-only fields accept input but are omitted from output. These directions help shape safe API contracts.

# Why this concept exists

Some values are generated by the server (IDs, timestamps, ownership); others may be needed to process a request but should not be echoed (passwords, one-time secrets). Directional fields make these rules explicit.

# Real-world analogy

A receipt number is written by the cashier and shown to the customer; a PIN is entered to authorize an action but never printed on the receipt.

# Internal Working

During deserialization, DRF skips read-only fields and validates write-only fields. During representation, DRF emits read-only fields and omits write-only fields.

# Request Lifecycle (where applicable)

```text
POST body -> write_only accepted -> validation -> create
instance -> read_only represented -> renderer -> response
```

# Syntax

```python
token = serializers.CharField(write_only=True)
created_at = serializers.DateTimeField(read_only=True)
```

# Complete Example 1

Assume a `User` model and an app with DRF installed. This serializer accepts a password but never returns it:

```python
# accounts/serializers.py
from django.contrib.auth import get_user_model
from rest_framework import serializers

User = get_user_model()


class SignupSerializer(serializers.ModelSerializer):
    password = serializers.CharField(
        write_only=True,
        min_length=12,
        trim_whitespace=False,
    )

    class Meta:
        model = User
        fields = ["id", "username", "password"]
        read_only_fields = ["id"]

    def create(self, validated_data):
        return User.objects.create_user(**validated_data)
```

```python
# accounts/views.py
from rest_framework import generics
from .serializers import SignupSerializer


class SignupView(generics.CreateAPIView):
    serializer_class = SignupSerializer
```

```python
# accounts/urls.py
from django.urls import path
from .views import SignupView

urlpatterns = [path("signup/", SignupView.as_view(), name="signup")]
```

**Line-by-line:** `get_user_model()` respects the project's configured user model. Password is write-only and has a minimum length; `trim_whitespace=False` avoids silently changing a secret. Meta allowlists fields and protects ID. `create` uses Django's password-aware manager to hash the password; it does not store plaintext. The generic create view validates and saves.

**Request → Serializer → Validation → Database → Response:** parser reads JSON -> serializer validates username/password -> create_user hashes password and inserts user -> response representation includes ID/username but excludes password. **Internal working:** `write_only` affects representation and input visibility, but secure hashing is provided by `create_user`. Removing that method may invoke generic model creation and store an unusable/plain password value incorrectly.

**Professional use case:** User registration with hashed credentials and no secret echo.

# Complete Example 2

A server-owned timestamp:

```python
class AuditSerializer(serializers.ModelSerializer):
    created_at = serializers.DateTimeField(read_only=True)

    class Meta:
        model = AuditRecord
        fields = ["id", "action", "created_at"]
        read_only_fields = ["id"]
```

The output contains the timestamp but clients cannot set it through this serializer. Ensure the model/default or server logic creates it; serializer read-only does not create a value by itself.

# Complete Example 3

A confirmation value accepted for an action but not echoed:

```python
class ConfirmSerializer(serializers.Serializer):
    confirmation_code = serializers.CharField(write_only=True, max_length=64)
    accepted = serializers.BooleanField(read_only=True)
```

The view uses the code to verify an operation and can represent the result as `accepted`. Never log the write-only input. Marking a field write-only does not encrypt it in transit or storage.

# Advanced Example

Use `extra_kwargs` for simple ModelSerializer direction rules:

```python
class Meta:
    model = Profile
    fields = ["id", "display_name", "created_at"]
    read_only_fields = ["id", "created_at"]
```

For a field requiring custom options or validation, declare it explicitly. Review generated field configuration rather than assuming direction.

# Under the Hood

Serializer fields expose `read_only`/`write_only` flags. Representation iterates readable fields; input conversion ignores read-only fields and includes write-only values in validated input but excludes them from serialized output.

# Performance Notes

Directional flags have negligible cost. Secret handling, password hashing, and related validation have meaningful runtime cost and should be profiled under realistic loads.

# Best Practices

- Make server-owned fields read-only.
- Make secrets write-only and use secure processing.
- Hash passwords with the configured password hasher.
- Test both input acceptance and output omission.

# Common Mistakes

- Returning passwords or tokens in API output.
- Assuming read-only fields get populated automatically.
- Assuming write-only means encrypted.
- Storing password input through generic `ModelSerializer.create`.

# Debugging

Inspect `repr(serializer)` and test `.data` after save. Confirm field appears in the right direction and persistence code applies required transformations.

# Interview Questions

1. What does read-only do? Output-only serializer field.
2. What does write-only do? Input-only serializer field.
3. Does write-only secure transport? No; HTTPS and safe handling are still required.
4. Why override user create? To call password hashing behavior.

# Chapter Summary

Directional fields control what clients may send and receive. Protect server-owned values and secrets explicitly, while implementing the correct persistence/security behavior behind the serializer.
