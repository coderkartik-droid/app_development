# Introduction

A Hive `TypeAdapter<T>` encodes and decodes a custom Dart type. It tells Hive which stored fields correspond to an object's constructor values.

# Why this concept exists

Disk stores bytes and primitive structures, not live Dart object references. An adapter makes the object-to-storage mapping explicit and repeatable.

# Real-world analogy

An adapter is a bilingual interpreter: it translates a Dart object into a stored format and translates that format back into the correct object.

# Internal Working

Hive asks an adapter to write fields to a binary writer and later read them from a binary reader. Each adapter declares a unique type ID. The reader/writer protocol and generated code vary by Hive version; follow the exact package version's API.

# Syntax

An annotation-driven model commonly looks like:

```dart
@HiveType(typeId: 12)
class Task {
  @HiveField(0)
  final String title;
}
```

Generated adapter registration commonly uses `Hive.registerAdapter(TaskAdapter())`.

# Complete Example 1

This focused example shows a version-appropriate generated adapter setup. Add Hive annotation/generator dependencies and run code generation; `task.g.dart` is generated, not handwritten here.

```dart
import 'package:hive/hive.dart';
part 'task.g.dart';

@HiveType(typeId: 12)
class Task {
  const Task({required this.id, required this.title});

  @HiveField(0)
  final String id;

  @HiveField(1)
  final String title;
}

Future<Box<Task>> openTasks() async {
  Hive.registerAdapter(TaskAdapter());
  return Hive.openBox<Task>('tasks');
}
```

### Line-by-line explanation

- `hive.dart` supplies Hive types and annotations.
- The `part` directive links generated adapter source.
- `@HiveType(typeId: 12)` assigns a unique stable type identifier.
- The constructor requires both fields, preventing incomplete model construction.
- `@HiveField(0)` and `(1)` assign stable serialized field IDs.
- `TaskAdapter` is generated by the configured code generator.
- The adapter is registered before opening the typed box.
- The returned box is typed to `Task`.

### Widget tree

No widget tree is needed for adapter registration; a repository can call `openTasks` during app initialization.

### Execution flow

```text
Annotated type → generator emits adapter
Startup → register adapter → open task box → decode/encode Task values
```

### Example explanation

The stable IDs allow Hive to identify the type and each field even if source-code layout changes. If the adapter is absent, Hive cannot construct `Task` from stored bytes. If an ID is reused, old data can be decoded incorrectly.

**Common mistakes:** Code generation must run after model changes; generated output should not be edited manually.

**Professional use case:** Persist custom domain objects in typed boxes while keeping serialization concerns outside UI code.

# Complete Example 2

Register multiple adapters once during startup:

```dart
Hive.registerAdapter(TaskAdapter());
Hive.registerAdapter(ProjectAdapter());
```

Ensure type IDs are unique and registration is not duplicated inconsistently during hot restarts.

# Complete Example 3

When an optional new property is introduced, deserialize absent data with a default. Generated adapter options depend on tooling/version; inspect generated code and test compatibility instead of assuming a default exists automatically.

# Advanced Example

An adapter is part of the on-disk schema contract. Reserve ID ranges for features, maintain a schema compatibility matrix, and test reading real fixtures from older releases. If a field's meaning changes, migrate the value rather than reusing its identifier.

# Under the Hood

The adapter's type ID identifies the serialized class. Field IDs identify individual values within it. The binary reader/writer encode/decode the data, and Hive invokes the registered adapter when materializing the typed value.

# Performance Notes

- Keep adapter logic simple and deterministic.
- Avoid expensive computation during decoding.
- Use lazy loading for large values when supported.
- Keep custom object graphs bounded.

# Best Practices

- Generate adapters using project tooling.
- Register before opening boxes.
- Keep type and field IDs stable.
- Provide backwards-compatible defaults/migrations.
- Test old serialized fixtures.

# Common Mistakes

- Type ID collision.
- Renumbering fields after release.
- Forgetting generated files.
- Editing generated code directly.
- Assuming an adapter handles semantic migrations.

# Debugging

- Check generation command output and `part` filename.
- Verify adapter registration order.
- Check unique IDs across the whole app.
- Test with data written by a previous model version.

# Interview Questions

1. What does a TypeAdapter do? Converts custom objects to and from Hive storage.
2. What is a type ID? A stable serialized identifier for the Dart type.
3. What is a field ID? A stable identifier for one stored object field.
4. Why is registration order important? Hive needs the adapter before decoding typed values.
